# 8. Проверка конфигураций

Поддерживаемые протоколы:

- VLESS;
- VMess;
- Shadowsocks;
- Trojan;
- Hysteria2;
- TUIC.

Реализуй отдельные уровни:

1. Синтаксическая проверка.
2. Проверка доступности TCP endpoint.
3. Проверка реальной работы протокола.
4. Проверка выбранных пользователем сервисов.
5. Измерение ping.
6. Измерение скорости.

Обязательно различай:

- синтаксис корректен;
- TCP доступен;
- протокол успешно проверен;
- сервис доступен;
- проверка не выполнена;
- конфигурация не прошла проверку.

TCP-доступность никогда не должна автоматически означать работоспособность протокола.

Для проверки протокола допускается изолированный локальный процесс с временным localhost SOCKS-прокси и контролируемым HTTPS-запросом.

Не изменяй системные маршруты, DNS, VPN-подключения Windows и сетевые настройки ОС.

После проверки завершай временные процессы и очищай временные ресурсы.

Если компонент не поддерживает конкретный транспорт, сообщай об этом честно.

Не выдавай неподдерживаемую проверку за успешную.

- скорость отдачи, если измерялась.

Скорость измеряй реальным контролируемым тестом с ограниченным объёмом данных.

Учитывай:

- размер теста;
- длительность;
- погрешность;
- состояние сети;
- таймауты;
- неудачные измерения.

Не записывай нулевую скорость, если измерение вообще не выполнялось.

Не сравнивай результаты, полученные совершенно разными методами, как будто они равнозначны.

Показывай, почему конфигурация получила награду.

# 14. Отчёты — только по инициативе пользователя

Это принципиальное требование.

VPNDesk не должен самостоятельно отправлять отчёты, создавать GitHub Issues или публиковать диагностические сведения.

Отчёты касаются VPN-конфигураций, а не состояния самой программы.

Пользователь сам нажимает кнопку формирования отчёта и сам выбирает, что делать с результатом.

В отчёт должны входить:

- общее количество найденных конфигураций;
- количество проверенных;
- количество рабочих;
- количество нерабочих;
- протоколы;
- источники;
- результаты доступности выбранных сервисов;
- ping;
- измеренная скорость;
- причины отказов;
- рейтинг;
- обладатели корон;
- дата и время проверок;
- подробные результаты по конфигурациям.

Предусмотри несколько форматов:

1. Один полный TXT.
2. Два отдельных TXT: рабочие и нерабочие.
3. Настраиваемый отчёт, в котором пользователь выбирает разделы.
4. При необходимости JSON и CSV для машинной обработки.

Если пользователь хочет включить сами конфигурации, это должно быть отдельной настройкой с явным предупреждением о секретах внутри ключей.

Не включай IP владельца приложения, имя Windows-пользователя, имя компьютера, личные пути и другие личные сведения.

Не отправляй отчёты автоматически.

    mod.txt

mod.txt должен описывать:

- внешний вид;
- поведение;
- изменения;
- способ применения;
- способ отмены;

mod.json должен содержать машинно-читаемые настройки.

В первой версии разрешай декларативные изменения через безопасный список возможностей:

- темы;
- цвета;
- оформление;
- расположение элементов;
- настройки интерфейса.

Не запускай произвольные Python, BAT, EXE, DLL, JavaScript или другие исполняемые файлы из модов.

Перед применением:

1. Проверь структуру.
2. Проверь совместимость.
3. Покажи описание.
4. Покажи изменения.
5. Покажи предупреждение.
6. Предложи предварительный просмотр.
7. Запроси подтверждение.

При отключении или удалении мода восстанавливай базовое состояние приложения.

Удаление мода никогда не должно удалять базу данных, конфигурации, историю источников или пользовательские настройки.
